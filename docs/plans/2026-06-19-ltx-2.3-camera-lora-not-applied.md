# LTX-2.3 camera-control LoRAs silently not applied (no camera motion)

- **Date:** 2026-06-19
- **Status:** Diagnosed (root cause confirmed); fix not yet implemented
- **Severity:** Feature broken — the "LTX Camera" preset produces no camera motion (Flow *and* Batch mode)
- **Scope:** Model/container side. **Not an app-code bug** — frontend/backend/worker pipeline is correct.

## Summary

The per-direction camera-control LoRAs (`ltx-2-19b-lora-camera-control-{static,dolly-in,dolly-out,dolly-left,dolly-right,jib-up,jib-down}.safetensors`) are trained for **LTX-2 19B**, but the deployed workflow runs the **`ltx-2.3-22b-distilled_transformer_only_fp8_scaled`** transformer (22B / 2.3, fp8 distilled). ComfyUI loads the mismatched LoRA, its keys don't bind to the 22B architecture (`lora key not loaded`), and it **silently generates base-model-only output**. The job still completes → every camera column comes out identical with no motion.

## Symptom

In Batch mode with the "LTX Camera" preset (static / dolly-in / dolly-out / jib-up / jib-down across N images), all result columns look identical — no camera movement — and every job reports `done`/`COMPLETED`.

So the LoRA arrives at ComfyUI with the right name/format/wiring. The break is purely **base-model compatibility**.

## Root cause

- LoRAs: `ltx-2-19b-*` → **LTX-2 19B**.
- Model in workflow: `ltx-2.3-22b-distilled_transformer_only_fp8_scaled.safetensors` → **22B / 2.3, distilled**.
- ComfyUI behavior for a mismatched LoRA: logs `lora key not loaded` and produces **base-model-only output** (documented; called out specifically for LTX-2 LoRAs). Silent — job succeeds.

### Jef's reference workflow has the same mismatch
`comfy workflows from Jef/LTX-2.3_workflow.json` pairs `ltx-2.3-22b-distilled` UNET with `ltx-2-19b-lora-camera-control-static` @0.4 and has **no compatibility note**. Likely only "static" was validated (camera holds still anyway, so "no motion" looks correct) → dolly/jib silently doing nothing went unnoticed. Our `gpu-container-ltx/workflows/jef-ltx-2.3-i2v.json` is derived from this.

## Online findings (2026-06)

- **No per-direction camera-control LoRA exists for LTX-2.3 / 22B.** Lightricks' 2.3 control LoRAs are **IC-LoRAs** (`Union-Control` = Canny/Depth/Pose; `Motion-Track-Control` = sparse-trajectory/spline overlays). Different mechanism, different ComfyUI nodes (`LTXICLoRALoaderModelOnly` + `LTXAddVideoICLoRAGuide`, reference-frame conditioning).
- Official Lightricks guidance (LTX-2.3 discussion #15): use the **`Lightricks/ltx-23` IC-LoRA collection** for 2.3 control.
- Community thread: mixed reports ("2.0 LoRAs work fine" vs "dolly in/out work, left/right don't"). Probable explanation: those who saw it work were on the **full** 2.3 model, not the **fp8 distilled** transformer we deploy.
- Community tip: lower CFG improves camera responsiveness (we're already at cfg 1 on the distilled model).

## Fix options (ranked)

1. **Prompt-only camera control + strip the dead LoRAs (recommended for now).**
   Keep the preset names/prompts ("slow dolly in, camera pushing forward") but **remove `high_noise_loras` for LTX** so they don't silently fail. LTX-2.3 has good prompt adherence for camera moves. Zero workflow rewrite.
   - Frontend: drop the `highNoiseLoras` from the LTX Camera preset (or strip in `buildVideoAlgoParams` ltx branch) — `frontend/src/components/pages/studio/constants/action-presets.ts`.
2. **Run camera LoRAs on the full (non-distilled) LTX-2.3 model.** Test whether the 19B/2.0 camera LoRAs bind there (community reports suggest yes). Keeps the per-direction preset UX; changes the deployed model variant in `gpu-container-ltx`.
3. **Integrate the official 2.3 Motion-Track-Control IC-LoRA.** Proper, future-proof, but biggest effort: new ComfyUI nodes/workflow in the worker (`LTXICLoRALoaderModelOnly` + `LTXAddVideoICLoRAGuide`), reference-frame/trajectory inputs, and new UI (trajectory overlays) — not a 1:1 replacement for the strength-dropdown preset UX.
